# 开发约定

给要动这个仓库的人。约束**不可违反的前提**、**本地怎么跑门禁**、**踩过的环境坑**。

实现方式与停止条件见 [`plan.md`](plan.md)，选型依据见 [`research.md`](research.md)，
落库字段见 [`schema.md`](schema.md)。

---

## 1. 红线

违反其中任何一条，改动都要返工。每条后面是它的由来 —— 都是实测出来的，不是设计洁癖。

### 1.1 `exit_code == 0` 时绝不扫输出文本

成功的命令输出里出现 `error` / `failed` 字样是常态（编译器打印警告、测试框架汇总
skip、grep 命中含 error 的行）。早期版本对成功命令也扫文本，报错率虚高到
**20.3%**，改成只在非零退出码时扫，落到 **15.6%**。

### 1.2 脱敏占位符必须是 shell 安全裸词

用 `REDACTED`，**不要引入 `<` `>`**。带尖括号的占位符会被 shell 语法当成重定向符，
下游解析随之降级 —— 实测有 **294 条 mkdir** 因此被判成解析失败。

### 1.3 源库一律只读

以 `mode=ro` 打开。源库是外部工具的生产库，体积在 GB 量级，且有后台进程正在写入。
任何写操作都可能破坏别人的数据，也可能让本工具读到撕裂的页。

### 1.4 脱敏发生在落库之前

不是查询时过滤，是写入时就已经脱敏。测试 fixture **只准用合成凭据**，
不要从真实会话里裁一段当样本。

### 1.5 运行时依赖上限 4 个

`tree-sitter-bash` / `tree-sitter` / `drain3` / `duckdb`，全部 MIT。
不引入 GPL —— `bashlex` 因此被否。加第 5 个依赖前先问「能不能不加」。

### 1.6 证据分级不可混

这是整个工具的立身之本：

| 产物 | 分级 | 能不能引用 |
| --- | --- | --- |
| `report` / `summary` | 事实 | 可以 |
| `candidates.json` | 恒为 `exploratory` | **不可**计入任何质量声明 |
| triage `status` | 恒为 `unverified` | 同上 |

**本工具不判定「某条命令是否必要」** —— 那需要反事实实验。它只把几万条命令压缩成
几百条值得做实验的线索。任何让 candidates 看起来像结论的改动，都是在拆这条底线。

## 2. 本地门禁

```bash
./scripts/check.sh
```

这是唯一权威入口，它用 pin 版本覆盖 CI 的全部检查（Python 三件套 + 前端
typecheck + `shell.html` 同步校验）。**别用系统装的 ruff/mypy/pytest** ——
版本漂移会造成「本地过、CI 挂」：实测本地 ruff 0.15 放过的 UP038，CI 的 0.9.2 会报错。

两个 venv 分工不同，别搞混：

| 路径 | 用途 | 注意 |
| --- | --- | --- |
| `.venv-ci/bin/*` | 跑门禁的 pin 版本工具 | **没装 cmdaudit**，不能用它跑 CLI |
| `.venv/bin/cmdaudit` | 真跑 CLI | |

`check.sh` 硬依赖网络（要 `pip install -e '.[dev]'`）。断网时的表现是**挂住，不是
快速失败** —— 卡很久别以为是测试慢。

### 单独跑某一项时

- **mypy 必须裸跑**（`pyproject.toml` 已限定 files）。手敲 `mypy src tests` 会看到
  test 文件里若干早已存在的报错，那些不在门禁范围内。
- **千万别整仓库跑 `ruff format`** —— 会重排大量文件，产生巨大的无关 diff。
  `ruff format` 不在门禁里，格式只由 `ruff check` 约束。

### `src/cmdaudit/viz/shell.html` 是构建产物

它必须与 `web/dist/index.html` 逐字节一致，CI 有专门一步校验。所以：

- 改前端后跑 `scripts/sync-shell.sh` 重建外壳再提交。
- **合并冲突时不要手工解** —— 随便取一边，然后重新构建同步。手工解出来的产物
  必然与源码不一致，一致性检查会红。

## 3. 环境坑

- **macOS 没有 `timeout`**。写脚本时别假设它存在。
- **zsh 不做未加引号的变量分词**，glob 无匹配时的报错习惯也与 bash 不同。
  照 bash 习惯写的片段在 zsh 里行为会变。
- **对源库跑长 SQL 会超工具超时**（120 秒量级）。拆小查询，或者放后台跑。
- **SQLite `LIKE` 对 ASCII 不区分大小写**。查键名大小写要用 `GLOB` 或改用 Python
  遍历 —— 某个 agent 用大写 `Cwd` 而非 `cwd` 就是这么被发现的，此前该 agent 的
  工作目录覆盖率一直是 0%。

## 4. 改统计口径时

口径变了，**旧数字全部作废** —— 包括 README 里的、issue 里引用的、以及任何截图。

这不是洁癖。历史上同一份数据在不同口径下的差距是量级级别的：可信耗时合计能从
39.72 h 缩到 10.66 h（p90 从 11.0 s 到 3.54 s），失败判定的分母口径一改，
失败率从 2.9% 走到 4.1%。数字本身不说明谁对，但**混着用一定错**。

配套动作：

1. 改完用**同一快照**重跑全量 `extract` + `report`，再据此重写 README 数字。
2. **不要中途逐步对数** —— 源库一直在增长，口径与快照时刻是两个纠缠的变量，
   拆不开。中途对不上是正常的，说明不了任何事。
3. 一句话说清新旧口径的差别，写进 PR 描述。

有几笔口径修正正在分批落地（见 issue #6 / #12 / #13 / #17 / #30），期间 README
数字与最新代码可能短暂不一致 —— 以合并后的重跑结果为准。

## 5. 验证基线

合并任何改动前：`./scripts/check.sh` 全绿。CI 是事实来源，本地门禁只是它的镜像。

涉及抽取或统计逻辑的改动，额外要求**全量 `extract` + `report` 能跑通**（不只是
测试绿）—— 单测覆盖不到真实数据的形状多样性，很多问题只在全量跑时才露头。
